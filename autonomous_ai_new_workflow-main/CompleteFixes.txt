# Comprehensive Master Changelog (v1 to v9)
This document aggregates all fixes, architectural changes, and optimizations applied to the Semantic Layer Analytics AI, spanning from the initial v1 codebase up to the v9 Query-Pipeline Reliability & Theme Compliance release.

---

## Part 1: V1 Core Refactoring & Autonomous AI Consolidation
*These fixes stabilized the initial query routing architecture, consolidated the AI logic into a single Autonomous AI pipeline, and fixed multiple edge cases in the LLM planner.*

### 1. Verification & Bug Fixes
- **SIMPLE fallback → UNKNOWN**: Added `UNKNOWN` mode classification. Queries that don't match any catalog objects now gracefully return a guided error instead of entering endless LLM loops or throwing "KPI Required".
- **AMBIGUOUS column mapping**: Fixed missing `column` field in the AMBIGUOUS response payload so the UI properly displays the conflicted column name.
- **Frontend Mode Badges**: Styled the `direct_select` and `autonomous-ai` badges uniformly across the UI sidebar and results cards.
- **GREETING mode alignment**: Ensured `"CONVERSATIONAL"` was fully mapped to `"GREETING"` across both the classifier and UI renderer.
- **Simple Query Resolution**: Bypassed strict SIMPLE mode routing when queries contain aggregations (e.g. "sum of"), sending them to the AI planner (`COMPLEX` mode) instead of crashing the direct select pipeline.
- **Multi-Agent Recursion Limit (AI Planning Error)**: Loosened semantic validation string matching (`getDynamicColumn`). The LLM planner can now slightly misspell columns (e.g. `"Samount"` instead of `"S_amount"`) and the backend will autocorrect it, preventing 8-loop recursion crashes.

### 2. "Autonomous AI" Architecture Consolidation
- **Removed Legacy Pipelines**: Deleted `kpiPipeline.ts` and `directSelectPipeline.ts`.
- **Unified Entry Point**: Renamed `deepAgentWorkflow.ts` to `autonomousAi.ts` and funneled all valid queries through `runAutonomousAi`.
- **UI Simplification**: Removed the manual "mode selector" dropdown in the frontend. The UI now fully operates in `autonomous-ai` mode implicitly.

## Part 2: V2 Security, Frontend, and Resilience Updates
*This phase introduced essential security patches, telemetry concurrency fixes, and Tailwind CSS v4 frontend compatibility.*

### 1. Security & Dependencies

- **API Authentication Middleware**: Secured all `/api` routes via `mcp/security/authMiddleware.ts` requiring `process.env.API_KEY`.

- **Memory Leak in Conversations**: Stripped massive data rows from `msg.queryResult.data.rows` before saving conversation history to memory.

### 3. Frontend Fixes
- Fixed arbitrary CSS variables by replacing `-([color])/40` with valid `color-mix` functions for Tailwind v4 compatibility.
- Fixed `lazyWithRetry` React router loader to forcibly reload `sessionStorage` on chunk load errors.
- Applied API key headers (`VITE_API_KEY`) globally across Axios interceptors.

### Sprint 8: Backend Hardening (Adapters & Legacy)

- **SQL Server Foreign Keys**: Fixed broken multi-column FK queries by migrating from `INFORMATION_SCHEMA` to strict `sys.foreign_key_columns` mappings.
- **Legacy KPI Guardrails**: Evaluated legacy KPIs containing string-based `inclusions/exclusions` and properly flagged them with `needsMigration: true` preventing backend crashes.
- **Automated Telemetry Cleanup**: Deployed `cleanupOldTelemetry` in `main.ts` on a 24-hour interval to delete logs and latency samples older than 7 days to prevent database bloating.

## Part 5: V5 Master Bug Fixes & Refinement
*This phase systematically resolved the final 78 outstanding bugs listed in Frontendproblems.txt across security, LLM planner routing, compiler generation, telemetry bottlenecks, and database adapters.*

### 1. Security & Routing
* **API Key Headers & Hardcoded Secrets**: Modified `authMiddleware.ts` to strictly require `x-api-key` headers (removing query parameter fallback) and changed the default API key to generate a secure random token on startup instead of using "default-dev-key".
* **Missing Routes**: Implemented the missing `POST /conversations` endpoint in `router.ts` to wire up the conversation creation feature.
* **Rate Limiting & Proxy Support**: Added `trust proxy` to the Express app configuration to ensure IP-based rate limiting functions correctly behind load balancers. Applied `apiLimiter` to exposed routes including `/api/observability/logs`, `/metrics`, `/circuit/:id`, and the SSE `/stream` endpoint.
* **Payload DoS Protection**: Lowered the `express.json` and `express.urlencoded` body limits from a dangerously high 50MB down to 1MB to prevent memory exhaustion DoS attacks.

### 2. System Orchestration & LLM Planner
* **Model Routing**: Refactored `getLlmModel` to fix silent overrides, ensuring `gpt-*` models are correctly respected and `semantic-slm`/`verifier-slm` map to appropriate fast models (like `llama-3.1-8b-instant` or `gpt-4o-mini`).
* **Error Propagation**: Fixed a severe bug where `AMBIGUOUS_KPI_MODE` was swallowed by LangGraph. The orchestrator now explicitly captures `fatalError` in its state and re-throws it so the UI's ambiguous fallback triggers correctly.
* **Metric Leakage & Race Conditions**: Prevented dynamic-metric mutation leaks in `validatePlan.ts` so duplicate metrics don't pile up in the catalog. Fixed concurrent race conditions on metric auto-healing.
* **Planner Schema Fixes**: Adjusted `QueryPlanSchema` to default to ascending (`asc`) sort directions for time-series queries. Prevented the `insightBuilder.ts` from hardcoding "monthly trend" suggestions when a dataset has no date column. Removed deep unions in `LaxQueryPlanSchema` to improve structured output reliability for Groq/Llama models.

### 3. Compiler & KPI Logic
* **List Queries**: Fixed list queries by falling back to selecting `kpiOptions.kpi.select_columns` (if present) or `*` rather than throwing an `EMPTY_SELECT` error when a query lacks an explicit metric.
* **Update Validation**: Removed restrictive conditionals in `kpiMetrics.update` so that formulas, join specs, and logic rules are thoroughly validated on every update, even if only the name changed.
* **Column Validation (`filter_logic`)**: Enforced strict `table.column` matching checks in `kpiMetrics.create` to stop cross-table column leaks during validation.
* **Dead Code**: Removed the unused `extractInvolvedTables` and `validateFilterFragment` functions.
* **Query Overrides**: Modified `compileKpiQuery` to correctly respect `queryGroupBy`, `querySortDir`, and `queryLimit` overrides from `kpiOptions`.
* **SQL Server Generation**: Fixed the regex issue for SQL Server dialects by prepending `TOP N` directly during the initial `SELECT` builder phase rather than relying on a fragile regex substitution.
* **Self-Test Harness**: Disabled the `compiler.ts` test infrastructure from running automatically in production unless explicitly invoked with the `--selftest` flag.

### 4. Telemetry & Resilience
* **Log Performance**: Replaced O(N) `unshift` operations in `inMemoryLogs.ts` with `push` and `slice` to operate like a ring buffer, drastically reducing CPU/GC overhead.
* **IO Bottlenecks**: Increased the telemetry cache debounce timer from 1s to 5s to reduce filesystem pressure on heavy loads. Delayed the `cleanupOldTelemetry` chron by 5 minutes on startup to prevent lock contention.
* **Circuit Breaker Skew**: Added a clock-skew safeguard to `circuitBreaker.ts` to prevent negative timestamps (from NTP syncs) from permanently breaking decay calculations.
* **PostgreSQL Metadata UPSERT**: Verified that `telemetryStore.ts` uses a cross-database compatible UPSERT mechanism (trying `UPDATE` first and falling back to `INSERT`) rather than the MySQL-specific `ON DUPLICATE KEY UPDATE`.

### 5. Database Adapters
* **SSL Overrides**: Modified `buildLiveAdapter.ts` to extract `ssl` properties from the connection's `credentials_json`, allowing per-connection SSL behavior to override the global environment variables for Postgres and MySQL.
* **MSSQL Encryption**: Removed the hardcoded `encrypt: false` for SQL Server connections. It now defaults to true (required for Azure SQL) and respects `encrypt` overrides passed via `credentials_json`.
* **Snowflake Database Support**: Added extraction of the missing `database` parameter from `credentials_json` to pass into `snowflake.createConnection`.
* **SQLite Path Traversal**: Tightened SQLite path traversal protections by using `fs.realpathSync` to properly resolve and block symlink escapes.
* **Adapter Pool TTL**: Fixed the adapter pool race condition in `adapterPoolRegistry.ts` by checking the TTL condition immediately prior to executing async closes during iteration.

## Part 8: End-to-End Architectural Migration to LLM-Driven Intent
*This phase replaced the brittle deterministic Regex intent classifier with a flexible LLM-driven architecture, enabling natural language understanding of ambiguity, table selection, and basic data lookups.*

### 1. Stripping Brittle Routing Logic
* **Query Classifier (`queryClassifier.ts`)**: Gutted the regex-based routing logic for `SIMPLE` and `AMBIGUOUS` queries (Steps 1, 2, and 4). Only `KPI` and `GREETING` modes remain deterministic. All other queries gracefully fall through to `COMPLEX` mode, delegating intent resolution entirely to the Autonomous AI.

### 2. LLM Planner Schema Upgrades
* **Query Plan Schema (`planner/index.ts`)**: Upgraded `QueryPlanSchema` and `LaxQueryPlanSchema` to formally support `errorMode: "AMBIGUOUS"` and `errorMode: "UNRECOGNIZED"`.
* **Ambiguity Details**: Added a structured `ambiguityDetails` payload (reason, candidateTables, column) so the LLM can precisely explain *why* a query is ambiguous and offer candidate tables for user resolution.

### 3. Dynamic Intent Resolution Prompts
* **Planner Prompting (`planner/index.ts`)**: Rewrote the system prompt's `dynamicRules` for non-KPI queries. The LLM is now explicitly instructed to handle intent resolution: mapping simple data lookups to `groupBy` fields (without hallucinating metrics), throwing `AMBIGUOUS` if a column exists in multiple tables without context, and throwing `UNRECOGNIZED` for completely out-of-bounds questions.

### 4. Autonomous AI Orchestration Updates
* **Agent Error Handling (`autonomousAi.ts`)**: Upgraded the `plannerTool` within LangGraph to intercept `AMBIGUOUS` and `UNRECOGNIZED` error modes from the LLM. It parses the `ambiguityDetails` payload, serializes it into a specific fatal error format, and aborts the agent loop early to save tokens and latency.
* **Graceful Fallbacks (`autonomousAi.ts`)**: Updated the orchestrator's global catch block to intercept the serialized `AMBIGUOUS_MODE` errors. It now correctly structures a rich JSON response with `candidateTables` and `message` so the frontend UI can render interactive table selection cards for the user to resolve the ambiguity.

## Part 9: V9 Query-Pipeline Reliability, LLM-Provider Hardening & Theme Compliance
*This phase was a full-repo bug audit of the current architecture — `runKpiAgentPipeline` (certified-KPI-only) + `runSimplePipelineV2` (deterministic, replacing the dead ReAct agent) — followed by a live-fire debugging pass after switching LLM providers away from an exhausted Cerebras trial quota. Every fix below was verified against a real connection/catalog, not just unit tests, and the full self-test suite (`sql/compiler.ts` + `tests/regression.test.ts`, 32 cases total) stayed green throughout.*

### 1. Query Router — the largest single source of "the pipeline is broken" reports
* **Pre-query keyword hijacking**: `classifyPreQueryIntent()` in `query.ts` used broad, unanchored regexes (`\b(today|date|day|time|now)\b`, `\b(you|help|...)\b`, `\b(hi|test|morning|...)\b`) that matched ordinary business questions — "What were total sales by **day**?", "Can **you** show me revenue by region?", "Show revenue this **morning**" — and returned a canned greeting/clock response *before* `connectionId` was checked or `mode` was honored, silently bypassing both pipelines entirely. Replaced with whole-message anchored patterns (matching the style the existing GREETING check already used) so only literal greetings/date-asks/help-asks short-circuit; verified against 26 test phrasings.
* **Single-word KPI over-matching**: investigated tightening `scoreKpiMatch()` so a KPI named e.g. "Revenue" wouldn't match on the bare word appearing anywhere in an unrelated sentence. Two different heuristics were tried and both regressed extremely common real phrasing ("What is our revenue this quarter?"); reverted rather than ship a fix that breaks everyday queries in exchange for blocking a rare edge case.
* **Conversation memory was collected but never used**: `conversationContext` (last topic, referenced tables/columns) was built from `conversationStore` and passed into `classifyQuery()`, which never once read the parameter — a dead argument. Neither `planKpiQuery()` nor `planSimpleQuery()` accepted it at all. Threaded it through both pipelines into the LLM planner prompts with an explicit "use this ONLY to resolve pronouns like it/that, never override an explicit mention" rule, so a pronoun-only follow-up ("what can we group it by?") after discussing a KPI now resolves correctly. Kept intentionally small: last assistant answer truncated to 400 chars + deduped table/column name lists — not the full transcript.
* **`forcedTableContext` was accepted, validated, then discarded** (`void forcedTableContext;`) even though the frontend's "ask about this table" flow genuinely sends it. Wired it up: reorders the catalog so the named table is planned first (biasing the LLM toward it without losing the ability to join a related table).

### 2. KPI Pipeline
* **Null aggregate rendered the literal word "undefined"**: a scorecard query with zero matching rows still returns one row with a `NULL` value (SQL aggregate-over-empty-group behavior), which `insightBuilder.ts` rendered as `"The Total Revenue is undefined."` via `null?.toLocaleString()`. Null-guarded every value interpolation in the answer/grouped-list/top-row text.
* **Certified KPI formula could be silently shadowed**: `resolveMetricAcrossDatasets()` checks per-dataset local metrics before the certified `global_kpis` entry; if any involved table had a same-named local metric, its (possibly different) formula won over the certified one with no warning. Certified `matchedKpi.expressionSql` is now always preferred.
* **Empty `involvedTables` silently defaulted to a random table**: `sanitizeAndCorrectPlan()`'s generic "no datasets → use catalog[0]" fallback meant a misconfigured KPI (no tables selected) would quietly compute against whatever table happened to be first in the catalog. Now fails loudly with a message telling the user to fix the KPI definition.
* **`needsLlmPlanning()` missed plural grouping words** (`\bregion\b` doesn't match "regions") — fixed to accept optional plural suffixes.
* Misleading "no filter was requested" driver text on the deterministic scorecard path now reflects the real, final filter list after dashboard/date filters are merged in.
* **Multi-column `GROUP BY` silently collapsed to one dimension**: `compileKpiQuery` aliased every group-by column as the same `"group_key"` (duplicate SQL column names — every driver keeps only the last one), so "revenue by region and category" dropped region entirely with no error. Fixed to emit `group_key_1`/`group_key_2`/... like the simple compiler already did.

### 3. Simple Pipeline (`runSimplePipelineV2`)
* **Almost every "total/sum/average of X" question crashed**: the plan sanitizer rewrites a dynamic `SUM(budget)` metric into a bare name `sum_budget` and stashes the real formula on a per-request catalog clone; the KPI compiler re-resolves that name back to its expression via the catalog, but `compileSimpleSelectQuery` never received the catalog at all, so it tried to resolve `sum_budget` as a literal column and threw `Unknown column reference`. Per product decision, an uncertified ad-hoc aggregate with no matching KPI now returns a `mode: "needs_kpi"` response naming the exact formula/table to create, instead of crashing or silently computing an uncertified number.
* **No join-path inference for multi-table simple queries**: `compileSimpleSelectQuery` had no catalog parameter and no BFS fallback, so a multi-table question with no explicit join could compile a query referencing a table never introduced via `FROM`/`JOIN`. Added the same catalog-driven `autoGenerateJoins` BFS the KPI compiler already used.
* **`detectWriteIntent` blocked read-only questions** containing common nouns that happen to match write-verb regexes ("the latest **update** on orders", "when was this **created**", "our order **drop**-off rate"). Replaced the bare word-boundary check with SQL-shaped patterns (`insert into`, `update x set`, `delete from`, ...) plus an imperative-position check, verified against 12 phrasings including the exact false positives above.
* **Ambiguous non-metric columns bypassed the disambiguation UI**: only messages containing the literal `AMBIGUOUS_MODE`/`AMBIGUOUS_KPI_MODE` sentinel got the structured picker response; an ambiguous groupBy/filter column threw a differently-worded error and fell through to a generic failure. `resolveColumnAcrossDatasets` now throws the same sentinel format.
* **Large-schema catalogs blew the model's context window**: the planner always sent the *entire* catalog (all tables' columns/relationships) as JSON on every call regardless of question scope. On a 73-table connection this alone exceeded a smaller model's context length outright (`context_length_exceeded`). Added `selectRelevantDatasets()`: scope the catalog to explicitly-named tables (+ one relationship hop, for joins) or recently-discussed tables from conversation context; only fall back to a capped slice of the full catalog when nothing is named.
* **Model correctly builds a plan but mislabels it as a metadata question**: smaller/faster models occasionally set a coherent `datasets`+`groupBy`/`metric` plan but still flag `errorMode: "UNRECOGNIZED"` and answer with a fabricated guess instead of running the query (e.g. "what are the names in the account table" → "The names are: id, name." with no query executed). Sharpened the prompt's METADATA-vs-DATA distinction with explicit contrastive examples, and — since prompt tightening alone didn't fully fix it on the smaller model — added a code-level safety net in both pipelines: if the plan actually looks coherent (real datasets + groupBy/metric), trust that over the model's self-reported `errorMode` rather than discarding it for a hallucinated answer.
* **Successful conversational answers were reported as failures**: `UNRECOGNIZED_MODE` with a `conversationalAnswer` (e.g. "what can we group this by?") is a legitimate, correct response, not an error — but it was logged as `[Simple/KPI pipeline] execution failed:` with a full stack trace and returned as `success: false, mode: "unrecognized"`, which the frontend rendered as a red "Pipeline Error" box around a perfectly correct answer. Now returns `success: true, mode: "assistant"` and only logs a real error for genuinely unexpected exceptions.

### 4. SQL Compiler & Executor (`sql/compiler.ts`, `executor/buildLiveAdapter.ts`)
* **The 30s query timeout was inert for 4 of 7 dialects**: `withTimeout()` fired an `onTimeout` side-effect on the timer but then kept `await`-ing the driver call regardless — sqlite/snowflake/bigquery/databricks had no `onTimeout` handler at all, so a hung query on those dialects blocked the request indefinitely. Rewrote to `Promise.race` the driver call against the timer so it actually rejects at 30s on every dialect, and added real cancellation where the driver supports it (statement `.cancel()` for Snowflake, job `.cancel()` via `createQueryJob` for BigQuery, session close+reopen for Databricks).
* **Databricks never bound query parameters** — the compiler emits `?` placeholders for it, but `executeStatement` never received `query.params`. Any filtered query sent literal `?` characters to Databricks SQL. Fixed to pass `ordinalParameters`.
* **Double-release masked the real error** on timeout for MySQL/Postgres (`onTimeout` released the connection with an error, then the unconditional `.finally()` released it again, throwing "already released" and hiding whatever actually failed). Added a `released`/`handled` guard flag.
* **"today"/"yesterday" filters dropped the time component**: `resolveRelativeTime()` bound the same bare date to both ends of the `BETWEEN`, which most engines parse as midnight — against a `DATETIME` column this matched only rows at exactly `00:00:00`. Expanded to full start-of-day/end-of-day bounds, matching the pattern `validatePlan.ts`'s date-equality path already used correctly.
* **Auto-generated joins could route through tables nobody asked for**: `autoGenerateJoins`'s BFS ran over the entire catalog graph, not just `plan.datasets`, so it could silently bridge through an unrequested table and change result cardinality. Restricted the BFS to only traverse tables already in the plan.
* Compiled-query `joins` metadata (shown in the frontend's SQL/Trace tabs) reflected the caller's *original* `plan.joins`, not the joins actually rendered into the SQL when auto-generation kicked in. `finalize()` now takes the real `activeJoins` used.

### 5. LLM Provider, Rate Limits & Schema Validation
* **Cerebras free-trial quota exhaustion mislabeled as "prompt too large"**: Cerebras' free tier caps at 30K tokens/min and only 1M tokens/day (see `inference-docs.cerebras.ai/support/rate-limits`); heavy testing exhausted the daily budget, and a broad `invalid_request_error` string match in `errorFormatter.ts` mislabeled every failure in that bucket — including ones unrelated to size — as "The KPI planner prompt was too large" (wrong even when the *simple* planner failed). Switched the active provider to the already-configured `GROQ_API_KEY`, then later to `llama-3.3-70b-versatile` for double the tokens/min and materially better instruction-following (traded for a smaller daily budget — know your provider's dashboard before a heavy testing session). Split the error branch into three accurate messages: real context-length overflow, tool-call schema mismatch, and generic provider rejection.
* **`LaxQueryPlanSchema`/`QueryPlanSchema` rejected valid model output outright**: `errorMode`, `conversationalAnswer`, and `ambiguityDetails` were `.optional()` but not `.nullable()`, unlike every other field in the same schema. Groq's tool-calling commonly emits explicit `null` for an absent optional field rather than omitting it — that mismatch failed Groq's own tool-call JSON schema validation and rejected the *entire* tool call, discarding an otherwise perfectly correct plan. This was the actual root cause behind a `context_length_exceeded`-labeled failure that turned out to be a schema bug, not a size problem. Added `.nullable()` to all three fields.
* **`resolveModel`'s groq branch silently ignored `LLM_MODEL`** when called with a planner alias (`semantic-slm`/`verifier-slm`) due to a `modelName ? undefined : ...` short-circuit that the cerebras/openai branches never had. Fixed for parity.
* Bumped `LLM_MAX_RETRIES` from 1 → 3 so a genuinely transient 429 (not a hard quota exhaustion) gets retried with the SDK's built-in backoff instead of failing on the first hit.

### 6. Data Integrity, Security & Route Hardening
* **Multi-schema catalog collision**: `buildAiCatalog` derived `datasetName`/`physicalTable` from the *connection-level* `schema` variable instead of each table's own `t.table_schema`. A connection with no `default_schema` (e.g. MySQL enumerating tables across every non-system database) collapsed same-named tables from different schemas — `db1.orders` and `db2.orders` — into one catalog entry, silently merging their columns and losing the schema qualifier needed to query the right one. Now qualifies by the table's own schema.
* **SQL injection surface in Databricks metadata introspection**: `fetchDatabricksMetadata` built `information_schema` queries via raw string interpolation of `default_schema` with hand-rolled escaping, the only dialect not using parameterized queries for this. Switched to `ordinalParameters`.
* **Unhandled promise rejection could hang KPI-creation requests**: `kpiMetrics.ts`'s `create()` handler had steps 2–9 (catalog fetch + all validation) sitting outside any try/catch, unlike every other handler in the file — a rejected `fetchMetadata()` call (unreachable DB, auth failure) would leave the request hanging with no response until client timeout. Wrapped in try/catch → `next(err)`.

### 1. Startup & Boot Correctness
* **`.env` loaded after the modules that read it**: `main.ts` called `dotenv.config()` as a normal statement, but tsx/esbuild hoists `import` statements above module-level code — so the entire `./server` import tree (secret crypto, auth middleware, DB pools) evaluated its module-level env checks against an *unloaded* environment. Symptoms: a spurious `CONNECTION_SECRET_KEY is missing` warning on every dev boot, and — with `NODE_ENV=production` — `secretCrypto.ts`'s module-load check would wrongly *crash the boot* when the key lived only in `.env`. Fixed by making `import "dotenv/config"` the very first import.
* **Auth key frozen at module load**: `authMiddleware.ts` captured `const VALID_KEY = process.env.API_KEY || "default-dev-key"` at import time. It only worked because `dataCatalog.ts` happened to call `dotenv.config()` earlier in the import chain; any import-order shift would silently freeze the fallback dev key as the only accepted credential (rejecting the real key, or accepting the default). Now reads the key per request via `getValidKey()`. Verified on a fresh boot: default key → 401, configured key → 200.
* **Unhandled rejection in telemetry cleanup**: the 24h `setInterval(cleanupOldTelemetry, …)` invoked an async function with no `.catch`, so a failed cleanup surfaced as an unhandled promise rejection. Wrapped like its `setTimeout` sibling already was.

### 2. LLM / Provider Error Labeling (`errorFormatter.ts`)
*The central `getFriendlyErrorMessage()` was mislabeling several AI-provider failures as "Database error", telling users to "review the KPI definition or generated SQL" for problems that were entirely upstream of the database.*
* **Provider HTTP 402 (out of credits / free-tier daily quota) → now an AI Services error** naming the real cause (add credits / wait for reset / switch provider) instead of the generic `Database error: 402 Provider returned error…`. This was hit constantly once the OpenRouter free daily cap was exhausted.
* **Upstream "Provider returned error" (free-pool serving partner failures)** → classified as an AI Services error suggesting a retry / model switch.
* **LangChain structured-output failures** (`Failed to parse`, `OutputParserException`, `Could not parse`) and **empty structured completions** → classified as AI Services errors ("output couldn't be parsed into a valid query plan") rather than falling through to `sanitizeDbError`'s "Database error:" prefix. Observed live: Cerebras' free `gpt-oss-120b` returns malformed/truncated structured output specifically on filter+join queries, while Groq `llama-3.3-70b` handled the identical queries cleanly.
* **Null/undefined error object** no longer throws inside the formatter (`String(error.message)` on a null error) — guarded to return a clean "No error details were provided" message.

### 3. Planner Null-Safety (`pipelines/kpi/kpiPlanner.ts`, `pipelines/simple/simplePlanner.ts`)
* **`withStructuredOutput` returning null crashed the planner**: both planners did `const result = { ...plan, groupBy: plan.groupBy ?? null }` immediately after `structuredModel.invoke(...)`. When a provider returned an empty/unparseable completion, `invoke` resolved to `null`/`undefined` and `plan.groupBy` threw a raw `Cannot read properties of undefined (reading 'groupBy')` TypeError — which then got mislabeled as a "Database error" downstream (see §2). Guarded both: a nullish plan now throws a clean "language model returned an empty query plan" AI-service error. Hit live on a Zepto relative-date query.

### 4. Classifier — Wrong-KPI "Measure Conflict" (`routes/semanticLayer/queryClassifier.ts`)
* **A KPI could be answered for a question that named a different measure**: "what is the total **rejected** quantity in the inbound report?" silently matched the **INBOUND Volume** KPI (`SUM(receivedQty)`) and returned that number with full confidence — because the classifier scored on shared nouns ("inbound"/"quantity"→"qty") and the discriminating word "rejected" carried no penalty, while the weak-match caveat only ever fired for single-word KPI names. Added `detectConflictingMeasure()`: when the question contains every distinctive (non-generic) token of a measure-like column that the KPI's formula does *not* aggregate, that KPI is skipped in favor of the next non-conflicting candidate; if all candidates conflict, the request falls through to `COMPLEX` (honest `NEEDS_KPI` / ad-hoc handling) rather than returning a confident wrong number. Deliberately conservative — "total inbound volume" and "… by region" never trip it, and a correct "Rejected Quantity" KPI (if one exists) still wins.
* **Warehouse columns are TEXT, not numeric**: the first cut keyed on semantic type `"number"`, but Zepto stores `receivedQty`/`rejectedQty` as TEXT (→ semantic type `"string"`), so the guard never fired live. Broadened to any non-date column whose *name* looks like a measure (carries a generic measure token like qty/amount/count), with configured KPI dimensions explicitly excluded so a legitimate "by <dimension>" is never mistaken for a measure conflict. Verified live: "total rejected quantity" now returns a `NEEDS_KPI` prompt to create `SUM(rejectedQty)`; controls ("total inbound volume", "picking accuracy") unaffected.

### 5. KPI Group-By Dimension Allowlist — Duplicate Column Names (verified, `analytics/orchestrator/analyticsOrchestrator.ts`)

### 6. KPI Filter Ambiguity — the group-by bug's twin on the WHERE path (`analytics/orchestrator/analyticsOrchestrator.ts`)
* **A qualified-but-guessed filter column silently filtered the wrong table**: the group-by allowlist protected grouping, but an equivalent hazard existed for filters. Wired into all three checkpoints where the dimension guard already runs (planner output, pre-sanitize, post-sanitize). Regression tests now cover typed, flat, nested-group, and single-table shapes.

### 11. SQL Compiler — Aggregate Fan-Out via Filter-Only Joins (`sql/compiler.ts`)
* **A COUNT/SUM KPI silently inflated ~5.8× when it joined a table only to filter on it.** Found on the real `gsconnectdev` "Volume Resolved" KPI: `COUNT(case.number)` with `INNER JOIN GS_SYS_USER ON case.assigned_to = user.name`, joined solely to apply the filter `user.web_service_access_only != 'true'`. `GS_SYS_USER.name` is non-unique (64 rows, only 23 distinct names — `csr_bom_01` appears 8×), so each case row fanned out ~5.8× (max 16×) and the COUNT ballooned. The KPI reported **123,373**; the true value is **21,397** (verified by direct SQL: case-only count = 21,399; `COUNT(DISTINCT number)` over the join = 21,311). Every result of the KPI was affected — total, monthly trend (~17K/month instead of ~3K), and every group-by.
* **Root cause**: the compiler already collapses an *existence-only* INNER JOIN into a `WHERE EXISTS` semi-join to avoid exactly this fan-out, but `shouldRenderJoinAsExists` treated ANY reference to the joined table — including a filter — as a reason to keep the real join (`references.allTables` included filter tables). A prior self-test even codified that ("fanout inner join remains when joined table is filtered"). That was incomplete: a filter on a filter-only table can be *pushed inside* the EXISTS.
* **Fix**: split table references into `nonFilterTables` (SELECT/GROUP/metric/time-grain — these still block conversion because the rows are consumed) vs. filter-only references. A join whose right table appears only in filters is now rendered as `EXISTS (SELECT 1 FROM right WHERE <join cond> AND <that table's filters>)`, with those filter units removed from the outer WHERE. Conservative guards preserve correctness: only `INNER` joins convert; a filter unit that mixes the joined table with another table (e.g. an OR spanning tables) can't be pushed, so that join falls back to a real join; and filters are matched/removed by AST-node identity so nothing is dropped or double-applied. Filter sources are flattened along top-level `AND` only (`flattenAndUnits`), so an `OR` is never split. Result SQL is byte-identical in the common (no-push) case.
* **Verified**: 4 new compiler self-tests (semi-join with pushed filter; mixed-OR keeps real join; mixed same-/other-table filters split correctly with exact param order; group-by on joined table keeps real join). Live on `gsconnectdev`: "volume resolved" now returns **21,397** with `WHERE EXISTS (... AND user.web_service_access_only != ?)` and no `INNER JOIN`; monthly trend and "in 2025" (18,151) also correct and still semi-joined; the ambiguous-`u_gsc_region` filter still correctly returns AMBIGUOUS. Full self-test suite: 27 compiler + 39 regression cases green.

### 14. Certified-KPI Routing Defect ("volume resolved based on u_gsc_region")
*A live gsconnectdev query "what is volume resolved based on u_gsc_region?" failed with two confusing, misleading errors on successive attempts: first "Query has 3 datasets but only 1 join(s)… gs_sys_user not reachable", then "Database error: Unknown column reference: volume_resolved". The KPI configuration was valid; the defect was entirely in routing and compilation, before any database execution.*
* **Root cause — false measure-conflict on a shared namespace token.** `detectConflictingMeasure` (queryClassifier.ts) treated the schema-prefix token `gsc` — shared between the requested dimension `u_gsc_region` and unrelated measure-like columns `u_gsc_amt_qty_1/2/3` — as evidence the user named a competing measure, so it rejected the exact `volume_resolved` KPI and routed to the Simple pipeline. Fixed: a candidate measure column's "distinctive tokens" now exclude every token that appears in the KPI's configured dimensions (`dimensionContextTokens`), so a shared namespace/prefix can never masquerade as a competing measure. The literal-column escape hatch (user types the real column name) is preserved.
* **Consequence 1 — disconnected multi-table Simple plan.** In Simple mode the planner picked an extra dataset; the orchestrator appended the KPI's two required tables but not its configured join, yielding 3 datasets + 1 join. `validatePlan` correctly rejected it (auto-heal only runs at zero joins). Now moot because the query routes to KPI mode, but also guarded by the reroute below.
* **Consequence 2 — certified metric hit the Simple compiler.** On retry, `volume_resolved` (a certified metric NAME, not an inline aggregate) reached `compileSimpleSelectQuery`, which searched for a physical column literally named `volume_resolved` → "Unknown column reference".
* **Fixes.** (a) `promoteCertifiedKpiPlan()` (analyticsOrchestrator.ts): if the Simple planner returns a plan whose metric matches a certified KPI name, promote it to the KPI profile — pin the KPI's datasets, joins, formula, filters, and dimensions — then re-run the dimension-allowlist and filter-ambiguity guards. (b) A hard compiler guard (`CERTIFIED_METRIC_REQUIRES_KPI`, compiler.ts) rejects a certified metric name reaching the Simple compiler with a clear "Internal routing error … no database query was executed" instead of a misleading "Unknown column". (c) errorFormatter no longer labels these pre-execution planning/routing failures as database/connection errors. (d) The KPI planner prompt now treats "based on X" as a group-by trigger.
* **Verified.** Live: "based on u_gsc_region" → clean AMBIGUOUS ("u_gsc_region exists in both gs_sys_user and gs_sn_customerservice_case — pick one") because both are configured dimensions; "volume resolved" still returns 21,397 via the semi-join; a qualified "case.u_gsc_region" grouping routes to KPI, compiles a GROUP BY, executes, and the result-quality guard correctly reports the source column is entirely null (a data issue, not code). ### 15. Orchestration Made Agent-Only (removed the deterministic tool-loop) — SUPERSEDED by §16
*Per request, the orchestrator now runs exclusively as a LangGraph ReAct agent — the agent calls the orchestrator's tools and decides which to call next — with no execution-mode toggle.*
* **Removed the `tool-loop` path.** Deleted `runToolDirectedOrchestrator()` (the deterministic backend loop that advanced tools by each tool's `next`) and the `ANALYTICS_ORCHESTRATOR_EXECUTION_MODE` branch in `runAnalyticsOrchestrator()`. Every request now always builds `createReactAgent({ llm: getLlmModel(), tools })` and invokes it; the agent selects each tool guided by the tools' structured `next`/retry/terminal results. The tools keep enforcing prerequisites/ordering and share backend-owned run state through the per-run queue, so the agent still can't run SQL out of order, skip validation, or fabricate results, and the API response is still assembled deterministically from state (the agent's final text is ignored).
* **Removed the env toggle** `ANALYTICS_ORCHESTRATOR_EXECUTION_MODE` from `.env`, `.env.example`, and all docs (README, workflow, project explanation). It is agent-only internally, not configurable. `ANALYTICS_ORCHESTRATOR_RECURSION_LIMIT` and `ANALYTICS_ORCHESTRATOR_MAX_TOOL_CALLS` still bound the agent loop.
* **Trade-off (documented).** Agent mode makes roughly one LLM call per tool (~8 per request) versus the ~1–2 of the old loop, so it consumes materially more provider quota and latency — size rate limits accordingly (especially on free tiers).
* **Verified.** `tsc` clean; 27 compiler + 49 regression tests green; live end-to-end (NVIDIA `llama-3.1-8b-instruct`) — the agent drove all eight tools in order for a scorecard KPI ("total inbound volume" = 10,320,701) and for the cross-table semi-join KPI ("volume resolved" = 21,397, `WHERE EXISTS`, no fan-out).

### 20. KPI Planner Prompt Gave the Model an Undocumented `errorMode: "AMBIGUOUS"` Escape Hatch
*Root-caused (not just retried past) the §19-style spurious-ambiguous rejection: "volume resolved for nov 2025" failed, but "what is volume resolved for nov 2025" succeeded — same filters, same KPI, only the interrogative framing differed.*
* **Root cause.** `errorMode: "AMBIGUOUS"` is a field the LLM sets itself in its own structured output (`z.enum(["AMBIGUOUS", "UNRECOGNIZED"])` in `planner/index.ts`). `kpiPlanner.ts`'s system prompt explains `"UNRECOGNIZED"` (metadata questions) but never once explains `"AMBIGUOUS"` or when to use it — unlike `simplePlanner.ts`, which defines it explicitly with two concrete trigger rules. For KPI queries this field is also structurally redundant: `resolveMatchedKpiPlanDimensions` and `findAmbiguousKpiFilterField` already deterministically catch every real case of a groupBy/filter column existing on more than one of the KPI's tables, *before* the code ever checks `plan.errorMode`. The model never needed this field for KPI mode; the prompt just never told it that.
* **Fix.** Added rule 11a to `kpiPlanner.ts`'s prompt: never set `errorMode` to `"AMBIGUOUS"` for a KPI query — the backend already owns that decision deterministically; populate `groupBy`/`filters` with exactly what the user asked for (per existing rule 11) and let the backend decide. The only valid `errorMode` for a KPI query is `"UNRECOGNIZED"`, per rule 12.
* **Verified.** 27 compiler + 71 regression tests green (prompt-string-only change; no guard logic touched). Live: the exact failing phrasing now succeeds reproducibly on Groq.

### 32. Null-First KPI Filters and Parent-Aware Join Branches

### 33. KPI Follow-Up Suggestions Recommended a Dimension That Didn't Exist (`pipelines/shared/insightBuilder.ts`)

The monthly-trend suggestion had the identical latent pattern (checked the raw table for any date-like column, not the KPI's configured date dimension) — it just hadn't misfired yet because `resolved_at` happened to be both.
* **Fix.** `metricDef` (already computed earlier in the same function for the "Based on the X KPI" context text, and already typed with `.dimensions`) is now reused for both suggestions on certified-KPI queries: a monthly-trend suggestion only appears for an unused, KPI-configured date dimension not already the active `timeGrainColumn`; a breakdown suggestion only appears for an unused, KPI-configured non-date dimension, and now **names it** (`"Break down volume resolved by region"` / `"...by service line"`, via a new `humanizeDimensionName()` that strips the `u_gsc_`/`u_` ServiceNow field-namespace prefix). Non-KPI/Simple-mode queries keep the original raw-catalog-column heuristic unchanged, since there's no dimension allowlist concept there.
* **Verified.** Backend `tsc --noEmit` clean.

  decision. The backend deterministically selects up to five real live-catalog
  display fields (business identifier, description, state/status, priority,
  and owner/assignee where available) and stores them in `select_columns`.
  Validation now rejects dataset-only raw plans, while both analytics compiler
  paths reject empty projections instead of ever emitting `SELECT *`.
* **Presentation:** the shared Analytics/Dashboard result card humanizes the
  actual selected keys, so the case result renders meaningful headings such as
  Number, Short Description, State, Priority, and Assigned To. Insights name
  the selected entity (“Returned 100 cases”), and the Dashboard-only schema
  trace includes the approved projection columns. The original company
  Dashboard shell and layout remain unchanged.

### 38. Certified-KPI wide-catalog preservation
* **Audited path:** the router’s matched KPI is supplied to
  `pruneCatalogColumns()`. It protects formula columns, dimensions,
  `select_columns`, every saved join condition, filter fields, primary keys,
  and catalog relationship keys. `planKpiQuery()` receives only the KPI’s
  configured involved datasets; normalization then re-pins the complete saved
  dataset and join lists, and compilation uses the stored formula/filter
  definition rather than model-authored SQL.
* **Regression proof:** a two-table, 418-column fixture with a prune budget of
  two columns verifies that all formula, display, join, dimension, filter, and
  key columns remain present on both tables and are passed to the KPI planner.
  Existing promotion/compiler cases continue to verify complete dataset/join
  pinning and stored-formula execution.
* **Verification:** 28 compiler cases and 95 regression cases pass (123 total);
  backend and frontend production builds pass.

### 39. Explicit KPI month filters could vary between identical runs
* **Live finding:** two clean Dashboard conversations asked the identical
  `volume resolved for nov 2025 ?` question. One provider plan omitted the
  requested month and returned the 21,397 all-time total; the next supplied the
  range and returned the correct November value of 2,879.
* **Fix:** named month/year periods (including abbreviated and hyphenated forms
  such as `nov 2025` and `December -2025`) are now converted before planning
  into an inclusive `between` filter on the matched KPI’s configured date
  dimension. The filter is passed separately as authoritative user intent, so
  the stored KPI definition remains pinned and the LLM cannot drop the period.
* **Trace:** the Dashboard schema decision now enumerates the validated
  certified column set derived from the KPI formula, dimensions,
  `select_columns`, joins, filter AST, and keys. Qualified references are
  resolved to the correct configured table even when another KPI table has a
  same-named column.

### 40. Explicit case-list request was hijacked by a partial KPI-name match
* **Observed failure:** `list the high priority cases that are resolved` matched
  `center-matched_resolved_cases` from only the generic tokens `resolved` and
  `cases`. The score (~72.5) exceeded the KPI threshold of 55 even though the
  question requested records and contained no aggregate intent. The existing
  measure-conflict guard correctly found no competing numeric measure, but it
  had no concept of list-versus-scorecard output shape. KPI normalization then
  correctly pinned the wrong KPI, making a one-row aggregate unavoidable.
* **Fix:** entity-list detection now lives in a dependency-safe shared module
  used by both classifier and Simple planner. Strong record wording
  (`list`, `display`, `which`, `what are`, `give me`) wins over a KPI match;
  weak `show` wording also stays Simple unless it contains the full matched KPI
  phrase. Aggregate wording remains KPI-eligible. The orchestrator independently
  blocks Simple-to-KPI promotion for entity-list intent.
* **Planner defense:** after the mandatory LLM call, a selected entity-list
  dataset is forced back to a metric-free explicit record projection even if
  the provider returns a KPI metric. Explicit conventional filters are grounded
  to the selected live dataset; the reported request becomes
  `priority = High AND state = Resolved`.
* **Verification:** the exact sentence is covered with a deliberately hostile
  KPI-shaped planner response, while full KPI-name `show` wording and
  `how many` aggregate wording are verified to stay KPI. All 124 active checks
  pass (28 compiler and 96 regression cases).
